# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added (sign-in during internet cuts)
- **New backup codes from My account**: admins with two-factor sign-in see how many unused backup codes they have and can make a new set of 10 with a current code from their authenticator app (a backup code is not accepted for this). The old codes stop working; the new ones are shown once with a print button. Audited, and counted against the same 5-wrong-codes lock.
- **Clock-drift warning**: a refused authenticator code that would be right 1 to 10 minutes away now tells the admin that a clock is off and by about how many minutes, and records a `mfa.clock_drift` security event with the offset. The code is still refused and counts as a wrong attempt.
- `docs/DEPLOYMENT.md`: what keeps working during an international internet cut, and setting a domestic time server (NTP) so admin codes keep working when `ntp.ubuntu.com` is unreachable.
- Tests: unit (drift found 3 and 5 minutes off, not inside the normal window, not beyond 10 minutes, not for a replayed code), integration (drift refused and recorded; new backup codes need a current app code, retire the old ones, are audited, and are refused without two-factor, for customers and for admins without an enrolment).

### Added (SMS)
- **Kavenegar SMS for customer sign-in codes**: `SMS_PROVIDER=kavenegar` sends the code with Kavenegar's Verify Lookup API and an approved template (`KAVENEGAR_API_KEY`, `KAVENEGAR_OTP_TEMPLATE`, server environment only, passed through Docker Compose). The key never appears in logs or errors; requests time out after 8 seconds without retrying and never follow redirects; a missing key or template leaves phone sign-in off instead of stopping the store. Setup steps in `docs/DEPLOYMENT.md`.
- Tests: unit (request format, number conversion, success and error answers, timeout, refused numbers and codes, no key in errors, configuration checks, environment parsing).

### Fixed (deployment)
- The image build no longer pulls the `docker/dockerfile` frontend from Docker Hub (the `# syntax=` line is removed; BuildKit's built-in frontend handles the secret mounts), so it works where Docker Hub is blocked.
- `admin:reset-link` run through the `migrate` service now gets `APP_URL`, so its one-time link points at the real domain instead of `localhost`.
- `docs/DEPLOYMENT.md`: database and Redis passwords are generated as hex (base64's `/` and `+` broke the connection URLs), the Ubuntu package names for Docker, Compose and BuildKit, a swap file for the build on small servers, and getting and renewing the certificate behind a CDN (the CDN keeps its HTTP-to-HTTPS redirect on, and both HTTPS server blocks in `deploy/nginx/clicksp.conf` now answer `/.well-known/acme-challenge/`).

### Added (Phase 7: page builder)
- **Page builder for the home page** (`/admin/page-builder`, `pagebuilder.edit` and `pagebuilder.publish`: Super Admin only). The home page is a list of sections from a fixed registry: banner slider, welcome section (title, text, logo, search box, colour), motorcycles, categories, newest products, latest articles, text (headings, paragraphs, lists) and a call-to-action box (title, text, button with a store path or https link, colour). Each section can be shown only on some screen sizes (mobile, tablet, desktop) and in one or both languages. Sections are added, edited, moved up or down and removed; every change is saved as the page's single draft, checked whole against the registry. The draft is previewed at `/preview/home` (signed-in builder admins only, not indexed) and published with an optional note; earlier published versions are listed and can be published again as a new version (history is never rewritten). Edits carry the draft they started from, so a second editor's stale change is refused instead of overwriting.
- Documents hold no HTML, styles, class names or scripts: props are length-limited text, numbers in a range, a colour from three tokens and links checked by the same rules as menus. A stored document that fails the check is never rendered (the published one or the default layout is used). Without anything published the home page shows the default layout, the same as before.
- Security review follow-ups: the "started from" token names the draft or, with no draft, the published revision, so a form opened before someone else published is refused; discarding and restoring check it too; the database allows one published revision per page (unique index) and moves a revision only draft → published → superseded, with its publication record fixed; a restored revision records where it came from (shown translated); control and bidi characters are refused in documents themselves and in links; the preview gets the strict per-request CSP; the draft audit entry keeps the edited props and a SHA-256 of the document.
- Admin forms keep what was typed when the server refuses it (they used to clear); after a successful save they show the saved values.
- Every change is audited. Tests: unit (registry refuses unknown types, extra props, `javascript:`/`data:`/protocol-relative links, oversize documents; form reading names the wrong field; typed markup stays text), integration (draft, stale edit refused, publish, second publication, rollback, exactly one published revision, published documents unchangeable, broken stored draft not rendered, Business Admin, Store Staff and customers refused), E2E (the Super Admin adds a box, previews, publishes, a visitor sees it in both languages and the typed markup as text; a Business Admin gets 403 on the builder and the preview).

### Added (Phase 6b: returns and refunds)
- **Customer returns** (on the customer's order page): within 7 days of delivery the customer picks how many units of each line to send back and why. One open request per order; a line is never returned more times than it was ordered (database trigger). The order shows "Return requested" meanwhile.
- **Returns in the admin** (`/admin/returns`, `return.manage`, Super and Business Admins): approve, or reject with a note the customer sees (the order goes back to delivered). When the goods arrive, each line is marked sellable (back on a chosen shelf as a `return` stock movement) or not; the order becomes "Returned" when every unit came back, otherwise "Delivered" again. A received return is closed by its refund, or without one (an exchange).
- **Refunds** (`refund.create`, Super and Business Admins, fresh two-factor check): recorded after paying the customer back by bank transfer or in cash (no gateway can refund until a real gateway adapter exists), from the return screen (the value of the returned units is suggested) or the order screen (for example a paid order that can't be sent). Refunds never add up to more than the order's total (database trigger, order row locked); the form carries a one-time key, so pressing twice records once. A full refund makes the order "Refunded" and releases stock still held for it. Every step is audited; refunds go to the outbox (`refund.completed`) for accounting.
- Tests: unit (return window, quantities left, value of returned units), integration (full flow with stock back on the shelf once under concurrent presses, partial and full returns, rejection, 7-day window, refund of an unsent paid order, idempotent refund under concurrent presses, refunds capped at the order total, Store Staff and customers refused, stale two-factor refused, unpaid orders refused), E2E (checkout flow extended: delivered, customer asks for a return, admin approves, receives and refunds). Security review follow-ups: the 7-day window counts from the first delivery (a rejection or partial return doesn't reopen it), a refund key from another order is refused, the amount is refused if the store's price unit changed while the form was open, customer requests are audited, the customer sees only their own safe view of a return.

### Added (Phase 6: stock transfers and counts)
- **Stock transfers** (`/admin/inventory/transfers`, `inventory.transfer` on the warehouse): a transfer goes draft → on the way → received, or is cancelled. Shipping writes `transfer_out` movements at the source locations (refused when more than is free there, so open orders keep their stock); receiving writes `transfer_in` at the destination; cancelling a shipped transfer puts the stock back. Creating and editing a transfer needs the permission in both warehouses, shipping and cancelling in the source, receiving in the destination. Each step runs in one transaction under a lock on the transfer, so pressing a button twice ships once. Products are added by SKU (any spelling: digits, case and separators don't matter) and must be in the person's categories. Cancelling a transfer already on the way needs the permission in both warehouses. A transfer is one document: people limited to some categories see only those lines and can't act on a transfer holding other products. At most 500 lines per transfer.
- **Stock counts** (`/admin/inventory/counts`, `inventory.count`): a count lists every product with stock in a warehouse or one location; one open count per warehouse (database index). People type what they find, page by page; when a line is saved its expected quantity becomes what the system shows at that moment, so sales during the count aren't counted twice. Products the list doesn't have are added by SKU. Completing a count (`inventory.adjust`, Super and Business Admins) writes `count_gain` / `count_loss` movements for the differences in one transaction; a loss below what open orders hold is refused. Store Staff see only products of their categories. Saving a page again leaves lines whose count didn't change alone, so a difference found earlier is never lost. People who only count don't see the expected quantity (blind count). A count is cancelled by whoever started it or by an admin. Counts are limited to 5,000 lines (count one location at a time beyond that).
- Tests: integration (transfers: ship and receive once under concurrent presses, not more than is free, cancel returns stock, Store Staff limited to their warehouses and categories, customers refused; counts: differences applied with a sale during the count, products added, uncounted lines unchanged, Store Staff can't complete, one open count per warehouse, reserved stock protected), E2E (a Business Admin transfers between two warehouses and counts one). Security review follow-ups: re-saving a page keeps the difference, lines of another count or transfer and out-of-category lines are refused, in-transit cancel by the source alone is refused, an entry racing completion is either applied or refused.

### Added (Phase 6: product import)
- **Product import from CSV** (`/admin/imports`, `import.run`: Super and Business Admins). An admin uploads a UTF-8 CSV ("CSV UTF-8" in Excel, at most 2 MB and 5,000 rows) with the columns `sku, title_fa, title_en, short_fa, short_en, category, brand, price, compare_at_price, warranty_months, part_numbers, status`; a header-only template is at `/templates/products-import.csv`. A background job (`imports-process`, every minute and right after an upload or confirmation) checks every row against the catalog and writes a dry-run report (new, updated, refused rows with the reason) without changing anything. After the admin confirms, the same job applies the valid rows in order through the ordinary product services, acting as the admin who confirmed with their permissions at that moment, so each change is authorized and audited as if made by hand. A known SKU updates its product (empty cells keep current values); a new SKU creates a draft product (or an active one with `status=active`). Re-running a file only updates. The file is kept as a private file, never served by the media route.
- **Information pages are for Super and Business Admins only** (the owner's decision): `content.manage` is no longer held by Store Staff, a migration removes it from level-3 roles, and its highest level is now 2.
- Tests: unit (CSV reading: quotes, line breaks, BOM, non-UTF-8 refused, column checks, row checks), integration (dry run writes nothing; create, update and a second run of the same file; unusable files; cancel; a confirming admin who is disabled stops the import; Store Staff and customers refused; Store Staff refused on information pages), E2E (a Business Admin uploads, reads the report, confirms and the product exists).

### Added (Phase 6: background jobs and search indexing)
- **Background jobs** with pg-boss (12.40, in the app's own database, schema `pgboss`), started with the app (`instrumentation.ts`): outbox delivery every minute, expiring unpaid orders every 5 minutes (checkout still does it as it goes), and a nightly search rebuild. `JOBS_ENABLED=false` turns them off.
- **Outbox delivery** (`src/modules/jobs`): due events are claimed with `FOR UPDATE SKIP LOCKED` under a 5-minute lease, so two runners never take the same event and a runner that dies hands its events back. Only topics with a handler are claimed; failures are retried with a growing delay and parked as `failed` after 10 attempts.
- **Search indexing** (`src/modules/search`): with `MEILISEARCH_HOST` set, the storefront search asks Meilisearch (v1.58) and shows the ranked products from the database; otherwise, or when it doesn't answer within 1.5 s, the database search answers. The index holds public fields only (titles, brand, SKUs and part numbers as written and normalized; no prices, costs or stock) and the engine returns ids only. Typos are forgiven in titles but never in part numbers. A database trigger writes one waiting `search.product_changed` event per changed product; the nightly rebuild fills a fresh index and swaps it in.
- CI runs a Meilisearch service for the search tests.
- Security review fixes: a product change still being saved locks the product's waiting search event, so the runner can't index the old state and lose the change; a runner whose claim was taken over can no longer mark the event; events are delivered in outbox order; a runner that fails to start cleans up and keeps retrying, and `/api/health` reports its state; shutdown is left to Next.js; the first index build no longer delays start-up; Compose takes a scoped Meilisearch key. ADR 0003 records running jobs in the app process.
- Tests: unit (200 in total), integration (230 in total; new suites for outbox delivery: done, retry, parked after the last attempt, one runner per event, lease takeover, late results ignored; search: one waiting event per product, a change in progress held back from the runner, indexing on change, removal on unpublish, part numbers with and without dashes, database fallback when the engine is down).

### Added (Phase 6b, part 6: online payment, gateway-ready)
- **Gateway contract** (`src/modules/payments/domain/gateway.ts`, from the iranian-ecommerce skill): initiate, parse callback, verify. Amounts are integer Rial; an adapter converts if its provider counts in Toman. No real provider is connected yet: Zarinpal or Zibal is added from the official docs once the store's merchant and sandbox credentials are supplied (`PAYMENT_PROVIDERS` lists the adapters a server may use; credentials go in `<PREFIX>_*` server variables, never in the database).
- A **test-only gateway** (`fake`) for development and tests "pays" instantly. The environment check refuses it in production.
- **Customers** pay for their own unpaid order from the order page (amount from the database, at most 10 attempts per order). The bank page is opened from script, so the strict `form-action 'self'` policy stays.
- **Callback** `/api/webhooks/payments/<provider>` (GET or POST): the attempt is found by our own reference and checked with the gateway server to server. Only the exact amount counts. One transaction marks the payment succeeded and the order paid, and writes `payment.succeeded` and `order.paid` to the outbox. A replayed or concurrent callback changes nothing. An order that stopped awaiting payment is never verified, so the gateway returns the money. Forged callbacks, amount mismatches and reused references are recorded as security events; every callback is logged.
- **Admin:** `/admin/payments` lists gateways; a Super Admin (with a fresh MFA check) switches them on or off, audited. The order screen shows an order's payments to admins with `order.view_payment`.
- Security review fixes: one payment per order is checked with the bank at a time, and while it is the order can't expire, be cancelled or start another payment; callbacks must carry the gateway's token for the attempt; money that can't be applied is recorded as owed back (`payment.refund_required`); rejected callbacks are limited per IP; the test gateway runs only in development on a local address.
- Tests: unit (190 in total), integration (213 in total, a new payments suite covering payment, replay, two payments at once, decline, wrong amount, forged callbacks, the per-IP limit, cancelled orders, payments in progress and denied access), the checkout E2E now pays through the test gateway.

### Added (Phase 6, part 2a: images)
