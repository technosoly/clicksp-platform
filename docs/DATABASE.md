# Database

PostgreSQL 16+ (CI and Docker use 17), Prisma 7 for the schema and client, hand-written SQL for everything Prisma cannot express. This document describes what is implemented (Phase 3). The entity diagram is in [ERD.md](ERD.md).

## Files

| Path | What it holds |
|---|---|
| `prisma/schema/*.prisma` | The schema, one file per area: `system`, `identity` (identity, RBAC, audit), `catalog`, `vehicles` (motorcycles and fitment), `inventory`, `sales`, `accounting` (accounting and payments), `shipping`, `content` |
| `prisma/migrations/20261126000000_init_extensions` | `pg_trgm` |
| `prisma/migrations/20261126100000_core_functions` | `gen_uuid_v7()`, `set_updated_at()`, `forbid_update_delete()`, `forbid_delete()`, `app_actor_id()` |
| `prisma/migrations/20261126100100_schema` | All tables, enums, indexes and foreign keys, generated by `prisma migrate diff` |
| `prisma/migrations/20261126100200_constraints_triggers` | CHECK constraints, triggers, the period exclusion constraint |
| `prisma/seed.ts`, `prisma/seed/system-seed.ts` | Idempotent system seed |
| `src/modules/rbac/domain/permission-catalogue.ts` | Permission keys and default role bundles (seed source) |
| `src/modules/settings/domain/default-settings.ts` | Required settings and their initial values (seed source) |
| `tests/integration/` | Integration tests that run against a real database |

## Commands

| Command | Does |
|---|---|
| `pnpm db:deploy` | Apply migrations (`prisma migrate deploy`) |
| `pnpm db:seed` | Run the system seed (safe to repeat) |
| `pnpm db:drift` | Fail if `prisma/schema` and the applied migrations differ |
| `pnpm db:validate` | Validate the Prisma schema |
| `pnpm test:integration` | Recreate the schema in `TEST_DATABASE_URL`, migrate, seed, run `tests/integration` |

The Docker `migrate` job runs `prisma migrate deploy` and then the seed. Changing the schema: edit `prisma/schema/*.prisma`, run `pnpm prisma migrate dev --create-only --name <verb_noun>`, add the SQL rules the change needs to that migration, and keep `pnpm db:drift` empty.

## Conventions

- **Keys:** UUIDv7 from `gen_uuid_v7()` (time-ordered, not guessable). PostgreSQL 18's native `uuidv7()` can replace it later.
- **Names:** tables `snake_case` plural, Prisma models singular PascalCase with `@@map`/`@map`.
- **Timestamps:** `timestamptz`. `updated_at` is maintained by a trigger on every table that has it, so raw SQL writes keep it right too.
- **Soft delete** (`deleted_at`) only on catalog and content: manufacturers, brands, categories, products, variants, motorcycles, coupons, addresses, articles, pages, media. Uniqueness that must ignore deleted rows uses partial unique indexes (Prisma preview feature `partialIndexes`). Ledgers and financial records never use soft delete.
- **Money:** `BIGINT` integer Rial with a `currency_code CHAR(3)` (FK to `currencies`, only IRR is seeded) beside every amount group: variants, price history, carts, orders, refunds, coupons, payments, journal transactions, accounts, expenses, income, shipping rates, shipments, invoices, movement costs. No floats anywhere; values above 2^53 are stored exactly (tested).
- **Translations:** `<entity>_translations(<entity>_id, locale, ...)` with `UNIQUE(<entity>_id, locale)` and per-locale slugs `UNIQUE(locale, slug)`. Customer-facing entities use translation tables: brands, manufacturers, categories, attributes and options, products, motorcycles, payment and shipping providers, shipping methods and zones, articles, article categories and tags, pages, banners. Admin-only records (roles, warehouses, financial accounts, cash registers) store the name the admin typed. Image alt text is a `{fa, en}` JSON object with `fa` required (CHECK).
- **Rich text and builder documents** are JSONB validated by Zod in code; never raw HTML.
- **Foreign keys** all have an explicit `ON DELETE` (default `RESTRICT`; `CASCADE` only for pure child rows) and an index.
- **Acting user in triggers:** services run `SELECT set_config('app.actor_id', '<user uuid>', true)` at the start of a transaction. Triggers that write history (prices, order status, movements, postings) record it. `app.status_reason` and `app.approval_id` work the same way.

## Integrity rules enforced by the database

Each rule below has an integration test in `tests/integration/`.

### Identity, RBAC, audit
- Users are never deleted (disable instead). E-mail is stored lower-case, phone numbers in E.164, at least one identifier is required.
- Sessions and verification tokens store only SHA-256 hashes (CHECK on hex format).
- **Permission ceiling:** each permission has a `max_level`. A role can hold a permission only if `1 <= role.level <= max_level`, so no Business Admin or Staff role, system or custom, can ever hold a Super Admin-only permission (role management, system and security settings, deployments, backups, integrations, payment gateway configuration, page builder, full audit log). Customer roles hold no permissions. Lowering a ceiling or changing a role's level is refused when it would break this.
- System roles cannot be deleted or have their key, level or system flag changed.
- The last active Super Admin cannot be disabled, lose the role, or have the role deactivated.
- Scoped grants (`role_permissions.is_scoped`) are allowed only for permissions that have a scope type; scope rows must point at exactly one category or warehouse.
- An approval cannot be decided by the user who requested it.
- `audit_logs` is append-only and **hash-chained**: the trigger assigns `seq`, `prev_hash` and `hash = sha256(prev_hash || row)` under a lock, ignoring any values the app sends. `SELECT audit_logs_verify()` returns the first broken `seq`, or `NULL` when the chain is intact.
- `login_attempts`, `security_events`, `system_logs` are append-only.

### Catalog
- Variant SKU: `sku_normalized` (upper case, no separators) is unique among non-deleted variants; one default variant per product; price `>= 0`; compare-at price `>` price.
- Every price change is copied to `product_prices` (append-only) with the acting user and approval.
- Identifiers (barcode, OEM, manufacturer, alternative, superseded part numbers) keep the original `value` and a `normalized_value` used for lookup (trigram index for partial matches). Barcodes are unique; the same part number may appear on several products, which is how cross-references work.
- Category and article-category trees reject cycles; category `depth` is maintained by trigger (max 8).
- Attribute values must match the attribute's type; variant-level images, identifiers and attributes must belong to the same product.

### Motorcycles and fitment
- Hierarchy: manufacturer → brand ("make") → model → generation (`year_from`..`year_to`, inclusive, Gregorian; `year_to` NULL = still produced) → variant (engine cc, stroke, cylinders, cooling, fuel system, market, optional narrower years) → typed specifications.
- `product_compatibilities` links a product to **exactly one** of a motorcycle variant or a whole generation, optionally narrowed by years, with a fitment position and quantity. A source (`compatibility_sources`) is **required**.
- Years must lie inside the generation; narrowing a generation that would strand variants or fitment rows is refused.
- `verification_status` starts `unverified`; `verified` requires `verified_by` and `verified_at`. Changing what a verified row claims (product, motorcycle, years, position, source) drops it back to `unverified`.
- Lookups by motorcycle use the `(motorcycle_variant_id, verification_status)` and `(motorcycle_generation_id, verification_status)` indexes (asserted with `EXPLAIN` in tests).
- `customer_vehicles` is "my garage" (one primary bike per customer).

How this supports the storefront structure Sogand chose (shop by motorcycle make → model → year → variant with parts grouped by system, shop by category, part-number search): top-level part categories flagged `is_vehicle_system` are the "systems" (engine, brakes, electrical, ...); a bike's parts are the verified fitment rows joined to the product's categories.

### Inventory
- `inventory_balances` (one row per variant per location) can **only** be changed by the triggers on `inventory_movements` and `stock_reservations`; any other write is rejected. New balance rows start at zero.
- CHECKs: `on_hand >= 0`, `reserved >= 0`, `reserved <= on_hand`. `available = on_hand - reserved` is computed, never stored.
- Inserting a movement (quantity `> 0`, direction from its type: receipt, issue, sale, return, transfer in/out, adjustment plus/minus, count gain/loss) creates the balance row if needed, updates it under the row lock and stores `on_hand_after`. A movement that would make stock negative fails and nothing is written. Movements are append-only; transfer movements must reference their transfer.
- Reservations are created `active` (`reserved += qty`, fails when not enough is available) and can move once to `consumed`, `released` or `expired` (`reserved -= qty`); closed reservations are immutable. For a sale: consume the reservation, then insert the `sale` movement.
- Concurrency: 12 parallel checkouts for 5 units in stock produce exactly 5 reservations (tested).

### Sales
- Orders are created `pending_payment`. Status changes follow the state machine below and each change (including creation) writes `order_status_history` with the acting user and reason. Orders are never deleted.

  | From | Allowed to |
  |---|---|
  | pending_payment | paid, cancelled |
  | paid | processing, cancelled, refunded |
  | processing | shipped, cancelled, refunded |
  | shipped | delivered, returned |
  | delivered | return_requested, refunded |
  | return_requested | returned, delivered, refunded |
  | returned, cancelled | refunded |

- `grand_total = subtotal - discount_total + shipping_total + tax_total` (CHECK). At commit, an order must have items, `subtotal = Σ unit_price × quantity` and `discount_total = Σ line discounts` (deferred trigger). Each line: `line_total = unit_price × quantity - discount_total + tax_total`.
- Order lines are snapshots (SKU, titles, attributes, price) that can only be added while the order awaits payment and never change. Amounts and coupon are frozen once the order leaves `pending_payment`.
- Returned quantity per line never exceeds the ordered quantity; refunds (excluding failed/cancelled) never exceed the order's `grand_total` (the order row is locked to serialize concurrent refunds). Refund requests carry a unique idempotency key.
- Invoices are immutable after issue except the e-invoice (Moadian) status fields, never deleted, one sale invoice per order; credit notes reference the invoice they correct.

### Payments
- One `succeeded` payment per order; `(provider, provider_reference)` and our own reference and idempotency key are unique, so a replayed callback cannot record a second success.
- Success requires `verified_at` and the gateway reference. Order, provider, amount and references never change; final rows (succeeded, failed, cancelled, expired) are immutable except for linking the journal entry once. Rows are never deleted. Raw callbacks are kept append-only in `payment_callback_logs`.
- Gateway credentials are **not** stored in the database; `payment_providers.credentials_env_prefix` names the server environment variables.

### Accounting
See [ACCOUNTING.md](ACCOUNTING.md). In short: journal entries are inserted into a **draft** transaction and then posted; at commit a posted transaction must have at least two lines and balance; posted transactions and their lines are immutable and undeletable; corrections are reversals (one per transaction); periods cannot overlap and closed periods accept no postings; postings go only to active, postable accounts in the transaction currency; `(source_type, source_id, source_event)` is unique so an event is posted once.

### Content
- Page revisions keep their document forever (immutable); published revisions cannot be deleted; a page can only publish its own revision.
- Media: allow-listed MIME types per kind (no SVG or HTML), SHA-256 recorded. Banner links must be relative paths or `https://`.

## Seeded data

Only system data, inserted idempotently: locales `fa` (default, RTL) and `en`; currency `IRR`; the 65 permissions of the catalogue; the four system roles (`super_admin`, `business_admin`, `store_staff`, `customer`) with default bundles; 8 store settings and 9 system settings with safe defaults (see `default-settings.ts`). Re-running the seed never overwrites admin changes: settings are inserted only when missing, and default grants are added only when a role or permission is new.

**Not seeded** (the owner enters real data): products, categories, brands, manufacturers, motorcycles, fitment, warehouses, stock, customers, orders, chart of accounts, tax rules, payment and shipping providers, shipping zones and rates, pages and menus. A test asserts these tables are empty after the seed.
