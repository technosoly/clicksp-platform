# Performance engineering

## Activation conditions
- New client component or dependency; caching/revalidation changes; list pages; heavy queries; search; images.
- CI performance budget failure.

## Purpose
The store must feel fast on a mid-range Android phone over a throttled 4G/3G connection.

## Budgets (CI-enforced where possible)
| Metric | Target (p75, mobile) |
|---|---|
| LCP | ≤ 2.5 s on "Slow 4G" Lighthouse profile |
| INP | ≤ 200 ms |
| CLS | ≤ 0.1 |
| Client JS (gzip) product/category | ≤ 150 KB |
| Server response (TTFB) cached page | ≤ 300 ms |
| Search API p95 | ≤ 150 ms |
| Admin list API p95 (50 rows) | ≤ 300 ms |

## Workflow
1. **Rendering**: Server Components by default; stream with `Suspense`; client islands small and lazy (`next/dynamic`) where below the fold.
2. **Caching**: catalog reads cached with tags (`product:<id>`, `category:<id>`, `page:<key>`), revalidated on admin writes via outbox handler. Never cache per-user data (cart, account, prices for logged-in special groups) in shared caches. Verify current Next.js caching semantics in the docs for the pinned version.
3. **Images**: `next/image`, correct `sizes`, AVIF/WebP, max width per breakpoint; originals stored, derivatives generated by worker; no images larger than needed.
4. **Fonts**: self-hosted, subsetted Vazirmatn, `preload` only the primary weight.
5. **Database**: select only needed columns; avoid N+1 (batch with `in` queries); cursor pagination for large tables; add indexes for every new filter/sort; check `EXPLAIN (ANALYZE, BUFFERS)` for new heavy queries; `pg_stat_statements` reviewed per release.
6. **Search**: Meilisearch for text queries; identifier exact match through DB index first; debounce input 200 ms; return only fields needed for the suggestion list.
7. **Third-party scripts**: none by default; analytics self-hosted and loaded after interaction/idle.

## Technical requirements
- `@next/bundle-analyzer` report in CI artifact; size-limit check fails the build when budgets are exceeded.
- Lighthouse CI on key pages with mobile emulation and throttling.
- Load test script (k6) for catalog, search and checkout initiation before production.

## Security requirements
- Caches must never mix users' data; cache keys never include secrets; `Cache-Control: private, no-store` on authenticated responses.

## Expected outputs
- Performance notes in PRs touching hot paths; budget configs; `docs/ARCHITECTURE.md` caching section kept accurate.

- Bundle size check in CI.
- Query tests asserting index usage for critical queries.
- Cache invalidation test: admin edits product → product page shows new data after revalidation; authenticated pages not cached.
